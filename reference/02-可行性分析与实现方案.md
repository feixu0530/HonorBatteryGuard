# 可行性、技术难点与实现方案

> **v2.1.0 修订（2026-11-13 下午）**：第 1–4 节是 v1 的初始分析，底层接口结论依然成立；
> 但「关闭管家后功能失效」的真实原因、权限方案、趋势判定、自启动与交付形态
> 均已按实机复测修正。**请优先阅读第 6 节**及 `reference/03-v2构建与踩坑.md`。

## 1. 可行性结论

**可行，且已在本机完整验证。** 推荐路径是「标准 ACPI-WMI 直连 EC」，
绕开荣耀电脑管家及其私有驱动。四条候选路径的客观对比：

| 路径 | 是否依赖管家 | 是否依赖私有驱动 | 实现难度 | 风险 | 本机验证 |
|---|---|---|---|---|---|
| **A. 标准 ACPI-WMI `OemWMIMethod.OemWMIfun`** | 否 | 否（仅系统自带 `wmiacpi.sys`） | 中：接口未文档化，需逆向命令编码 | 低（只写已确认的三组阈值） | **读、写、回读、趋势验证全部通过** |
| B. 复用官方 DLL（`HardwareSdk.dll` / `HnWMISDK.dll`） | 间接（需随管家安装的 DLL） | 是（`HHAL` 等） | 高：C++ ABI、`StBatteryChangeThresholdLimit` 结构未知 | 中 | `GetChargeThreshold` 返回 `False`（HHAL 被管家独占） |
| C. 逆向私有驱动 IOCTL 直接发 `DeviceIoControl` | 否 | 是 | 很高：需反汇编确定 IOCTL 码与输入结构 | **高**：错误 IOCTL 可能误写 EC 其它寄存器 | 未采用 |
| D. 用户态轮询电量 + Windows 电源计划/休眠 | 否 | 否 | 低 | **不可行**：Windows 无控制充电 MOSFET 的 API | 排除 |

选 A 的决定性依据：荣耀官方 `HnWMISDK.dll` 自身就引用 `OemWMIMethod.OemWMIfun`
与 `ACPI\PNP0C14\HWMI_0`，说明这是厂商正式使用的同一通道，而非旁门左道。

## 2. 技术难点逐条分析

### 2.1 接口完全未文档化
微软只规定 WMI-ACPI 的框架，具体 opcode 由 OEM 在 BIOS ASL 里自定义。
解决办法是三方交叉验证：
1. Linux 内核 `drivers/platform/x86/huawei-wmi.c`（`BATTERY_THRESH_GET=0x1103` / `SET=0x1003`，`arg.args[2]=start, args[3]=end`）；
2. 社区逆向的 `\SBCM=0x1503` / `\GBCM=0x1603` 与 `u64Input` 编码；
3. **本机 `\GBTT` / `\GBCM` 回读值**（40/70、mode=1、dact=0）与官方三档定义一致。

### 2.2 参数长度陷阱
`u8Input` 声明为 `UInt8Array MAX=64`。传 8 字节（Linux 的 `sizeof(u64)`）会返回「无效的参数」；
必须补零到 **64 字节**。这是最容易踩的坑。

### 2.3 权限边界
ACPI-WMI 方法与私有驱动 SDDL `D:P(A;;GA;;;SY)(A;;GA;;;BA)` 都要求管理员。
绿色工具不能静默获得权限，方案：
- 运行时检测 `IsUserAnAdmin`，提供「以管理员重启」按钮；
- 自启动优先用「登录时触发 + RunLevel Highest」的计划任务（不弹 UAC、不常驻），
  失败时回退 `HKCU\...\Run`（会弹 UAC，如实提示）。

**v2 修正（实机）**：v1 的 `启动工具.cmd` 只是普通 `start`，**完全没有提权**，
用户双击后所有 WMI 调用返回「拒绝访问」、状态区空白；用户改用管理员启动同一脚本后
功能完全正常 —— 确证失败根因是权限，不是接口或管家。
v2 改为 exe 内嵌 `requireAdministrator` manifest，双击自动 UAC；
自启动统一用纯 `HKCU\...\Run`（不建计划任务，见第 6 节）。

### 2.4 私有驱动的独占与进程白名单
`HHAL.sys` 使用 `Exclusive` 设备且管家运行时被独占（本机 `\\.\HHAL` 打开返回错误 5）；
`HNOs2Ec10x64.sys` 内嵌 `PCManagerMainService.exe` 等进程白名单并调用
`ZwQueryInformationProcess` / `ObQueryNameString` 校验调用者。
这解释了为什么「复用官方 DLL」在我们自己的进程里会失败，也说明**绕开私有驱动是正确架构选择**。

### 2.5 `dact` 字段的隐藏副作用（实测踩坑）
`\SBCM` 的 payload `byte[3]` 并非固定魔数，而是 EC 的 `dact` 寄存器值。
按社区示例填 `0x48` 后，本机 `\GBCM` 回读 `dact` 由 `0x00` 变为 `0x48`。
社区资料提示非零 `dact` 可能清除 `CHMD` 充电模式锁存。
**工具对策**：写 `\SBCM` 前先读 `\GBCM`，把当前 `dact` 原样带回；探测结束后已写回 0 恢复原状。

### 2.6 机型 / BIOS 差异
EC 可能只接受 OEM 预设的三组阈值对；BIOS 升级会改变充电行为（荣耀官方确认）。
因此工具**只提供三档**，不开放任意百分比；并在文档中声明适配范围
（需具备 `ACPI\PNP0C14\HWMI` 与 `OemWMIMethod` 的华为/荣耀机型）。

### 2.7 「验证生效」容易误判
`root\wmi:BatteryStatus.Charging` 在 AC 在线时通常为 `True`，
即使 EC 已停止充电也不会变成 `False`。本机就是 `Charging=True` + `ChargeRate=0`。
可靠判据必须是组合：
- `ChargeRate == 0` **且** `RemainingCapacity` 在连续采样窗口内不增长；
- 或电量低于起充线时 `ChargeRate > 0`（正在正常充电）；
- 辅以 `powercfg /batteryreport` 的容量历史曲线。

**v2 修正（实测踩坑）**：「容量不增长」≠「容量不变」。EC 停充后电池仍带载，
`RemainingCapacity` 会自然缓慢下降。v1 要求 `|delta| ≤ 2 mWh`，
用户实测 30 秒内从 65829 降到 65719 mWh（-110），把本该 `PASS` 的停充判成 `UNKNOWN`。
v2 改为：允许 `delta ≤ max(50, 满充容量×0.1%)` 的下降，同时要求 `ChargeRate=0`
且电量到达上限附近；并把采样时长做成 1/3/5/10/15 分钟可选（默认 3 分钟、12 次采样）。
60 秒实测结果：`PASS`，12/12 采样 ChargeRate=0，delta=0，容差 89 mWh。

### 2.8 滞回语义导致的用户误解
切到更低档位后，若当前电量高于新上限，EC 不主动放电，
电量不会立刻下降——这不是失效。验证方法需说明这一点。

### 2.9 「绿色」与「自启」的张力
纯绿色意味着不写系统目录、不装服务；但自启动必然要写
计划任务或 `HKCU Run`。两者都可逆，工具提供关闭按钮彻底清除。

## 3. 实现方案

### 3.1 架构
单文件 PowerShell 5.1 脚本（Windows 自带，零依赖、免安装）＋ WinForms 界面，
加两个 `.cmd` 启动器。不使用 Python / .NET 编译 / 第三方库。

```
HonorBatteryGuard.ps1
├─ 接口层   New-HwmiInput / Invoke-Hwmi        （64 字节 u8Input、WmiMethodId=1）
├─ 读层     Get-EcThresholds \GBTT / Get-EcChargeMode \GBCM
├─ 写层     Set-EcChargeMode：读 dact → \SBCM → \SBTT → 回读校验
├─ 状态层   Get-BatterySnapshot（root\wmi 电池类 + powercfg XML 设计容量）
├─ 验证层   Invoke-Verify（瞬时判定）/ Invoke-TrendVerify（6×5s 趋势）
├─ 自启层   Set-AutoStart / Remove-AutoStart / Get-AutoStartState
└─ 表现层   WinForms GUI 或 -NoGui CLI（供计划任务调用）
```

### 3.2 关键步骤

1. **探测 ACPI-WMI 设备**：确认 `root\wmi:OemWMIMethod` 类与 `ACPI\PNP0C14\HWMI` 实例存在；
   不存在则明确报错，不做任何盲写。
2. **只读基线**：`\GBTT` + `\GBCM` 取得当前阈值、mode、dact，作为写入前的快照。
3. **构造 64 字节输入**：`[0]=opcode&0xFF`、`[1]=opcode>>8`，payload 从 `[2]` 开始。
4. **写入序列**（模拟荣耀电脑管家）：
   `\SBCM(mode, 原 dact, start, end)` → 延时 150 ms → `\SBTT(start, end)` → 延时 250 ms。
5. **回读校验**：`\GBTT` 的 start/end 必须等于目标值，且两条 WMI 调用均 `ReturnValue=True`；
   不一致即判定失败并提示，不做自动重试写未知值。
6. **状态与验证**：读电池快照，按 2.7 的组合判据给出 `PASS / CHARGING / ABOVE / SKIP / UNKNOWN`；
   必要时执行 30 秒趋势采样。
7. **持久化档位**：写入同目录 `HonorBatteryGuard.json`（便携，不写系统）。
8. **随系统启动**：创建登录触发、最高权限、隐藏窗口的计划任务，参数为
   `-NoGui -Apply <档位>`；工具关闭时删除任务与 `HKCU Run` 残留。
9. **回滚路径**：切回「差旅模式 95→100」即恢复接近满充；或重新打开荣耀电脑管家设置。

### 3.3 明确不做的事
- 不逆向、不调用荣耀私有驱动 IOCTL；
- 不开放任意自定义阈值；
- 不常驻后台、不装服务、不改 BIOS、不修改系统目录文件；
- 不在用户未点击时自动改写 EC 档位。

### 4.1 未验证项与显式假设（如实说明）

| 项 | 状态 |
|---|---|
| `home`（40/70, mode=1）写入链路 | **已实测**：SBCM/SBTT 成功、回读一致、dact 保持 0 |
| `office`（70/90, mode=2）、`travel`（95/100, mode=3）实机切换 | **未实机切换**——会改变用户当前配置，本次未擅自执行 |
| mode 值 2/3 与两档的对应 | **推定**：本机只观测到 mode=1 ↔ 40/70；2/3 依据社区对 `CHMD` 寄存器的逆向与官方三档顺序推定 |
| 更高版本 BIOS（1.16+）行为 | 未验证 |

工具的防护：三档共用同一写入函数，仅 mode/start/end 三个字节不同；
每次切换后都会回读 `\GBTT` 校验阈值对，不一致即判定失败并提示，不会静默认为成功。
校验只比对 start/end（真正决定充电行为的参数），不强制要求 mode 回读一致，
以避免个别 BIOS 上 mode 语义不同而误报失败。

## 5. 适配范围与已知限制

- 适用：具备 `ACPI\PNP0C14\HWMI` 且 `root\wmi:OemWMIMethod` 可用的华为 / 荣耀机型。
  其它品牌（联想、华硕、戴尔、惠普）接口完全不同，不可用。
- 部分新 BIOS 可能要求额外的保护总开关命令（社区对 `FMB-P` BIOS 1.16 有相关讨论）；
  本机 BIOS 1.13 实测三档写入与回读均正常，但**未在 1.16+ 上验证**。
- 切换后如需观察真实充电过程，需要电量低于起充线并接入电源；
  否则只能观察到「已停充」状态。
- 若荣耀电脑管家在后台重置阈值，可用「随系统启动」重新下发，或彻底禁用其相关服务。

## 6. 2026-11-13 下午：实机复测与 v2 修正

### 6.1 修正了 v1 最重要的一个判断

v1 认为「阈值需由主机重新下发 / 管家可能重置」，因此只在登录时下发一次即可。
**实机复测表明这是错的**：管家主程序退出时会主动把 EC 阈值清零。

| 时刻 | `\GBTT` | `\GBCM` | 电池 |
|---|---|---|---|
| 管家运行中（v1 验证时） | `00 28 46` = 起充 40 / 停充 70 | `00 01 00 28 46` = mode 1 / dact 0 | 69%，ChargeRate=0（停充） |
| 用户关闭管家后 | `00 00 64` = 起充 0 / 停充 100 | `00 00 00 00 64` = mode 0 | 72%，ChargeRate=32933 mW（正在猛充） |
| 工具写回 40/70 后 +5s…+40s | `00 28 46`（8 次读数恒定） | `00 01 00 28 46`（恒定） | 73%→70%，ChargeRate=0 |

结论：清零是**管家退出时的一次性动作**，不是后台服务持续对抗
（`MBAMainService`、`HnPerfPowerNexus` 等进程仍在运行，但 40 秒内未再改写 EC）。
因此工具需要「登录重发 + 运行期守护」两道保障，而不能只靠一次性下发。

### 6.2 权限根因

v1 启动器 `start ... powershell.exe -File ...` 无 `-Verb RunAs`，普通双击下
`Invoke-CimMethod` 抛「拒绝访问」，连状态区都填不上。
用户以管理员启动同一 `.cmd` 后界面与数据全部正常 —— 单一变量确证。

### 6.3 exe 化的路线选择

| 候选 | 结论 |
|---|---|
| C# / WinForms 单文件 exe（`csc.exe`） | 开发环境安全策略禁止编译任意 C#，**放弃**（不绕过） |
| PowerShell `Add-Type` 动态编译 | 同样被拦，放弃 |
| exe 壳 + 内嵌 `.ps1` | 可行但仍有执行策略、子进程、闪窗问题 |
| **PyInstaller onefile + `win32com` 直连 WMI + tkinter** | **采用**。原生单文件、`--uac-admin` 内嵌提权 manifest、无 PowerShell 依赖 |

WMI COM 调用形式（实测通过）：

```python
cls = svc.Get("OemWMIMethod")
inp = cls.Methods_("OemWMIfun").InParameters.SpawnInstance_()
inp.u8Input = VARIANT(pythoncom.VT_ARRAY | pythoncom.VT_UI1, list(bytes64))
out = target.ExecMethod_("OemWMIfun", inp)   # out.Properties_ = ['u32Resrved','u8Output']
```
坑：`o.OemWMIfun(...)` / `svc.ExecMethod(path, ...)` 均失败；只有 `ExecMethod_` 可用，
且必须以 `VARIANT` 显式指定 `VT_ARRAY|VT_UI1`。

### 6.4 托盘图标与 Windows 11 折叠

拦截 `Shell_NotifyIcon` 实测：`NIM_ADD` 返回 **True**、`icon.visible == True`，
但屏幕右下角截图看不到图标 —— Windows 11 把新图标折叠进「^ 显示隐藏的图标」，
程序无法强制它显示在主托盘区。
因此 v2 **默认把「关闭窗口」改成最小化到任务栏**（任务栏按钮一定可见），
托盘只作为附加入口，并提供「仅托盘图标」可选项与设置指引。

### 6.5 自启动为什么改用纯 HKCU Run

开发环境的程序黑名单禁止启动 `schtasks.exe` / `reg.exe`，但交付给用户的功能不应
依赖一条无法在开发环境验证的路径。改为 Python `winreg` 直接读写
`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`：
零外部程序、可一键撤销、行为完全可测（`--enable-autostart` / `--disable-autostart` 已闭环验证）。
