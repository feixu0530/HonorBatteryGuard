# 电池安全管理的底层实现原理与系统接口依赖

> 本文所有结论均来自本机（HONOR MagicBook Pro 14 / `FMB-P` / BIOS 1.13 / Windows 11 26100）实测，
> 并与荣耀官方知识库、Linux 内核 `huawei-wmi` 驱动源码、社区逆向结果交叉验证。
> 探测时间：2026-11-13。

## 1. 结论先行

「电池安全管理」**不是 Windows 电源策略，也不是荣耀电脑管家在用户态轮询电量**。
它的本质是：**EC（Embedded Controller，嵌入式控制器）固件里硬编码的充电滞回策略**，
Windows 侧只负责把「起充阈值 / 停充阈值」这一对参数写进 EC。

因此该能力在架构上可以被完整剥离：只要能调用固件暴露的 ACPI-WMI 方法，
**无需电脑管家、无需荣耀私有驱动、无需常驻进程**。本机已实测打通该通道。

荣耀官方描述也印证这一点：更新 BIOS 后充电行为会变化（官方知识库 zh-cn15813840），
说明策略逻辑在 BIOS/EC，而非 PC 端应用软件。

## 2. 完整调用链

```
┌─ 荣耀电脑管家 UI (PCManager.exe / WebView2) ───────────────────────┐
│  设置 → 电源设置 → 电池安全管理 → 家用/办公/差旅                    │
└──────────────────────┬──────────────────────────────────────────────┘
                       │ IPC
┌──────────────────────▼──────────────────────────────────────────────┐
│ MBAMainService (PCManagerMainService.exe)                            │
│   plugins\PowerPolicyPlugin.dll / SmartChargePlugin.dll              │
│   注册表值：PowerSafeManagerStatus / PowerSafeManagerMode /           │
│             SmartChargeMode                                          │
└──────┬──────────────────────────────┬───────────────────────────────┘
       │ (A) 标准 ACPI-WMI              │ (B) 厂商私有驱动（性能/温控/PL1）
       ▼                               ▼
 HnWMISDK.dll / HardwareSdk.dll    \\.\HNOs2EcX64 (HNOs2Ec10x64.sys)
   GetWMIData(initializer_list\<uint8_t\>)   \\.\OS2SOC    (OS2SOC.sys)
   HardwareHal.dll (HalControl)              \\.\HHAL      (HHAL.sys)
       │
       ▼
 root\wmi : OemWMIMethod.OemWMIfun        ← 本工具走这条路
   GUID {ABBC0F5B-8EA1-11D1-A000-C90629100000}
   实例 ACPI\PNP0C14\HWMI_0 / HWMI_1
   驱动 wmiacpi.sys（Microsoft Windows Management Interface for ACPI）
       │
       ▼
 BIOS ASL 方法（DSDT/SSDT 中 HWMI dispatcher）
   \GBTT / \SBTT / \GBCM / \SBCM / \GBAD ...
       │
       ▼
 EC 寄存器（社区逆向：SCRS=0x80 / TCRS=0x81 / CHMD=0x85）
       │
       ▼
 充电 MOSFET → 电池实际充/停
```

**关键证据**：`C:\Program Files\HONOR\PCManager\HnWMISDK.dll` 的 UTF-16 字符串中
直接包含 `ACPI\PNP0C14\HWMI_0`、`OemWMIMethod`、`OemWMIfun`，
且导出 `HnWMI::GetWMIData(const std::string&, std::initializer_list<unsigned char>, std::string&)`。
即**荣耀官方自己就使用标准 ACPI-WMI 通道**。

## 3. 所需系统接口清单

| 层次 | 接口 / 对象 | 本机实测值 | 是否必需 |
|---|---|---|---|
| WMI 类 | `root\wmi:OemWMIMethod` | 存在，2 个实例 | **必需** |
| 类 GUID | `{ABBC0F5B-8EA1-11D1-A000-C90629100000}` | 与 Linux `HWMI_METHOD_GUID` 一致 | **必需** |
| WMI 方法 | `OemWMIfun`（WmiMethodId=1） | `u8Input UInt8Array MAX=64 [in]`；`u32Resrved UInt32 [out]`；`u8Output UInt8Array MAX=256 [out]` | **必需** |
| 扩展方法 | `OemWMIfunEx`（WmiMethodId=2，MAX=4128） | 存在，未使用 | 可选 |
| 事件类 | `OemWMIEvent` GUID `{ABBC0F5C-...}` | 存在 | 可选 |
| PnP 设备 | `ACPI\PNP0C14\HWMI` | OK，驱动 `wmiacpi.sys` | **必需** |
| 电池状态 | `root\wmi:BatteryStatus` / `BatteryFullChargedCapacity` / `BatteryCycleCount` / `BatteryStaticData`、`Win32_Battery` | 可用 | 只读 |
| 电池报告 | `powercfg /batteryreport [/xml]` | 提供设计容量 92041 mWh | 只读 |
| 私有驱动 | `HNOs2Ec10x64.sys`、`OS2SOC.sys`、`HHAL.sys` | 存在且 Running | **不需要** |

### 私有驱动侧的实际约束（说明为何绕开它们）

| 驱动 | 设备对象 | SDDL / 特性 | 本机打开测试 |
|---|---|---|---|
| `HNOs2Ec10x64.sys` | `\Device\HNOs2EcDevX64` / `\\.\HNOs2EcX64` | `D:P(A;;GA;;;SY)(A;;GA;;;BA)`；导入 `IoWMIOpenBlock`/`IoWMIExecuteMethod`/`MmMapIoSpace`；内嵌进程白名单 `PCManagerMainService.exe`、`PCManager.exe`、`MBAMessageCenter.exe` 等 | 管理员可打开 |
| `OS2SOC.sys` | `\Device\OS2SOC` / `\\.\OS2SOC` | `IoValidateDeviceIoControlAccess` | 管理员可打开 |
| `HHAL.sys` | `\Device\HHAL` / `\\.\HHAL` | `D:P(A;;GA;;;SY)(A;;GA;;;BA)`，`Exclusive` | **拒绝访问 (5)**：管家运行时被独占 |

`HardwareSdk.dll` 导出 `Battery::GetChargeThreshold` / `SetChargeThreshold`，
但在管家运行期间 `GetChargeThreshold` 返回 `False` 且不写输出缓冲（HHAL 被独占所致）。
这直接说明：**复用官方 DLL 反而不如标准 WMI 通道可靠**。

## 4. 命令编码（本机实测）

`u8Input` 前 8 字节等价于 Linux 内核的
`union hwmi_arg { u64 cmd; u8 args[8]; }`（小端），其余补零。

> **踩坑**：传 8 字节会返回「无效的参数」；`u8Input` 必须补齐为 **64 字节**。

| ACPI 方法 | opcode | `u8Input[0..7]` | `u8Output` 前几字节 | 实测结果 |
|---|---|---|---|---|
| `\GBTT` 读阈值 | `0x1103` | `03 11 00 00 00 00 00 00` | `[status, start, end, 0...]` | `00 28 46 00...` = 40 / 70 |
| `\SBTT` 写阈值 | `0x1003` | `03 10 start end 00 00 00 00` | `[00 00 ...]` | `retval=True` |
| `\GBCM` 读充电模式 | `0x1603` | `03 16 00 00 00 00 00 00` | `[status, mode, dact, start, end, 0...]` | `00 01 00 28 46` |
| `\SBCM` 写充电模式 | `0x1503` | `03 15 mode dact start end 00 00` | `[00 00 ...]` | `retval=True` |
| `\GBAD` | `0x1303` | `03 13 00 ...` | `[00 02 00...]` | 状态查询 |
| 智能充电 | `0x0202` | `02 02 00 ...` | `[00 00 45 ...]` | `0x45`=69，疑为当前电量 |

补充：社区公开的 `u64Input = 93803293775107`（设置 80→85）
解码为 `0x555048011503` → 小端 `03 15 01 48 50 55 00 00`，
即 `\SBCM` + mode=1 + byte3=0x48 + start=80 + end=85。
本机实测证明 **byte[3] 是 EC 的 `dact` 字段**：写入 0x48 后 `\GBCM` 回读
`dact` 从 `0x00` 变成 `0x48`。因此本工具在写 `\SBCM` 前先读 `\GBCM`，
**原样带回 dact**，避免副作用（该副作用已在探测后写回 0 恢复）。

## 5. 三档的准确语义：滞回区间，不是单一上限

| 档位 | mode | 起充 (start) | 停充 (end) | 官方说明 |
|---|---|---|---|---|
| 家用模式 | 1 | 40% | 70% | 长期接电源，最保护电池 |
| 办公模式 | 2 | 70% | 90% | 随时插拔，兼顾续航 |
| 差旅模式 | 3 | 95% | 100% | 长时间离电，接近满充 |

低到 `start` 才开始充电、充到 `end` 自动停止。
电量高于 `end` 时 **EC 不会主动放电**，只会随使用自然回落（官方知识库明确说明），
这是滞回设计，避免充电器频繁通断。

> 注意：官方只保证这三组 OEM 预设。社区在 `FMB-P` 上实测 EC 只对这些预设对
> 激活充电限制，任意阈值（如 60→80）可能只被存储而不生效。本工具因此**只开放三档**。

## 6. 权限与持久性

- **权限**：ACPI-WMI 方法与私有驱动 SDDL 均要求管理员（BA/SY）。工具检测 `IsUserAnAdmin`，
  非管理员时提供「以管理员重启」。
- **持久性**：阈值保存在 EC/CMOS，理论上跨重启保持；但管家退出或服务被禁用时可能恢复默认，
  且部分 BIOS 版本需要重新下发。这正是「关闭管家后失效」的根因。
- **设计取舍**：工具**不常驻**，只在「用户点击切换」和「登录时」各下发一次，
  用「随系统启动」覆盖冷启动后的重新应用。

## 7. 本机基线数据（2026-11-13 13:36）

| 项目 | 值 |
|---|---|
| 机型 / BIOS | HONOR MagicBook Pro 14 `FMB-P` / 1.13 |
| 电池 | `HB7075R5EHW-41T1`，设计 92041 mWh，满充 89961 mWh，健康度 97.7%，循环 62 |
| 当前档位 | 家用模式，`\GBTT` = 40/70，`\GBCM` = mode 1 / dact 0 |
| 电量 | 69%，AC 在线，`Charging=True`（ACPI 语义）但 `ChargeRate=0` |
| 30 秒趋势 | `RemainingCapacity` 恒为 62544 mWh，变化 0，`ChargeRate=0` |

**这组数据是「阈值确实生效」的直接证据**：Windows 报 `Charging=True` 只是因为 AC 在线，
真正的判据是 `ChargeRate=0` 且剩余容量在采样窗口内不再增长。
